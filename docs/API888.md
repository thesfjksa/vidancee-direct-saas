## Troubleshooting HTTP 400 (MiniMax H3 discounted image-to-video)

- `minimax-h3-480p-t` and `minimax-h3-768p-t` require **at least one public-accessible reference image URL** (up to nine). They require `seconds` as a **JSON string**, e.g. `"seconds":"5"`, **not** the numeric value `5` and not the `duration` field. 888API rejected the numeric value with `json: cannot unmarshal number into Go struct field .Alias.seconds of type string`. All 888API per-second SKUs use string `seconds`; fixed-price models retain numeric `duration`.
- The worker saves a safe `job.request_prepared` activity event with the model, selected length, and **image reference count** (not prompt, media URL, API token, or signed-link secret).
- Non-2xx 888API JSON errors are attached to `job.submit_failed` in Admin → Activity: `details.providerStatus`, `details.providerMessage`, and `details.providerRequestId`. Signed media URLs and credentials are redacted. This exposes the reason for a rejection that previously displayed only `888API request failed (HTTP 400)`.
- If the provider says it cannot fetch the reference image, verify Hostinger's outbound asset URL and public GET/HEAD access to `/provider-assets/{generationId}/{index}` with a signed query parameter. Do **not** paste signed URLs or the support key into chats/issues.
- A failed, rejected submission must be refunded; confirm Admin → Activity → refund for the generation. Do not blindly retry a paid request if the creation result is ambiguous.

## 4K image response size (October 24, 2026)

- 888API can return GPT Image 2.5 Sunburst 4K images **inline as base64 in JSON**. Those JSON responses often exceed the shared 4 MiB metadata response limit even when the final image is valid.
- `Api888Client.json` now accepts a request-specific bound: image generation JSON can contain one base64 image up to the existing 20 MiB decoded media limit, plus 64 KiB of JSON overhead (about 27 MiB total). Catalog, task submission, video polling and error bodies retain the **4 MiB** bound.
- Decoded image bytes must still be at most 20 MiB; MIME type, pixel dimensions, requested aspect ratio and MySQL ownership checks remain unchanged. No unlimited downloads and no customer-facing API key exposure.
- Existing rejected generation jobs have already been refunded and cannot be recovered from a lost provider response; retry a new generation only after the worker deployment succeeds.

## Live Admin task check (stuck processing diagnostics)

CMM Tools Admin → Generations now shows a **Check 888API** button beside the provider task ID of 888API video jobs. The button requests `GET /admin/api888/task-status?generation=<CMM generation UUID>` (Admin authenticated), which looks up the **existing saved task ID** and performs only `GET /v1/videos/{taskId}` using the encrypted provider token on the server. It does **not** create, retry, or bill a new video generation.

The result displays the local state, upstream state, progress (if returned), and whether local credits have already been refunded. If upstream says **completed** but local says **processing**, inspect worker `job.poll_failed` for download/storage failure. If upstream still says `queued` or `processing`, do not repeat paid creation. If upstream is `failed`, confirm the saved generation's refund.

Private output links, Bearer tokens, prompt text and signed reference URLs are intentionally omitted from the Admin endpoint's result. Some accounts may use alternate `task_status` aliases such as SUCCESS, FAILURE, SUBMITTED; the adapter interprets those where `status` is absent or unrecognized. An unknown state now emits a diagnostic error instead of silently remaining pending. This Admin status read cannot by itself rescue a completed file.

## Recover a completed 888API video after CMM Tools timed out

Example: CMM Tools job \`c2ebddd1-ab9b-4d25-805e-3f8d2c9c9627\` was marked **failed and refunded**, but 888API's read-only \`GET /v1/videos/{savedTaskId}\` confirmed **completed (100%)**. A normal worker cannot store this output after the refund because it only polls unrefunded, active jobs.

Admin → Generations → **Check 888API** now offers a second explicit confirmation to **Recover video** when the saved task reports \`done\` and the local generation is \`failed\` with an existing refund. Only an Admin can initiate the recovery; it cannot run for jobs that were not refunded.

The recovery:
- Uses the original saved task ID, first checks \`GET /v1/videos/{id}\`, then GETs its completed MP4.
- Does **not** initiate a paid \`POST /v1/videos\` and does **not** create another generation.
- Validates MP4 bytes through the existing 888API client; enforces the existing bounded media size.
- Inserts video into the existing transactional, user-owned \`generation_video_outputs\` and \`generation_video_chunks\` storage, updates the original job to \`completed\`, then it appears in the owner's Library.
- **Preserves \`refunded_at\` and the ledger refund** as a one-off goodwill recovery; the customer is not recharged.
- Is idempotent: if the video was already recovered, return success without duplicating chunks or credit changes; database \`FOR UPDATE\` protects concurrent requests.
- Writes a protected \`api888.video_recovered\` audit event with media size and task ID, never the provider token or signed media URL.

This only works while 888API still makes the completed video available. If the source asset has expired, an Admin must not repeat the paid POST automatically. Investigate whether the worker still cannot access 888API or whether the MP4 download fails before marking future generations as reliable.

## Completed-video recovery: download fallback and failure stage (Oct 24, 2026)

When an upstream video has \`completed\` status but the first provider result URL has expired or returns non-MP4 content, the 888API client now attempts the official authenticated \`GET /v1/videos/{taskId}/content\` endpoint using the **original saved task ID**. Both options are **GET-only**. The fallback can handle a redirect to a short-lived HTTPS MP4 and retains the 64 MiB output bound and MP4 signature validation.

For unsuccessful recovery, Admin gets a sanitized stage (\`video.status\`, \`video.download\` or \`video.storage\`) and, for download issues, a safe provider vs content-route summary; full details are logged to \`api888.video_recovery_failed\` in the protected Activity section. No signed URLs or provider API keys are sent to the browser or Activity.

Recovery remains an Admin-confirmed action limited to failed-and-refunded 888API video jobs whose upstream task is confirmed complete; it **does not** issue another \`POST /v1/videos\`, create new customer charges, or reverse existing refunds. If both retrieval routes are unsuccessful, the generation stays failed/refunded. This change does not prove that Hostinger can access the actual media; check the new error-stage detail if the original task still cannot be recovered.

## 888API completed media URL normalization (October 24, 2026)

An Admin recovery attempt for a provider-completed MiniMax H3 video returned **\`video.download\`**, with both direct provider URL and authenticated \`/content\` redirect rejected by the shared media URL validator as invalid. The exact URL format was not visible (correctly) because signed URLs must never be logged.

The 888API client now:
- Resolves **provider-relative** \`/v1/videos/{id}/content\` and \`v1/videos/{id}/content\` URLs safely against \`https://888api.xin\`.
- Supports protocol-relative \`//cdn.example/path\` HTTPS links.
- If 888API or a CDN returns a **public HTTP URL on the default port**, upgrades to **HTTPS** *before fetching* for DNS hosts. Completed-video public IPv4 exceptions are described below.
- Validates every resolved URL and every redirect with the existing media SSRF guard. **Rejects** localhost, private-style local names and credentialed links. DNS hosts remain HTTPS-only on the default port. The video-only literal public IPv4 exception below permits HTTP/HTTPS and custom ports.
- Preserves the existing 64 MiB MP4 limit, MP4 signature check, authenticated provider /content requests, and no-retry-of-paid-POST policy.
- On a still-unsupported URL, the protected error now includes only **shape**, **scheme**, **target type** and **port class**, never hostname, path, query, API token or signature. Share these fields instead of signed URLs.

These changes are safe compatibility improvements, not proof of the exact URL returned by the live task. If both download routes still fail, see Admin → Activity → \`api888.video_recovery_failed\`: a **public** HTTPS URL could be unreachable or the upstream URL could be unsafe and must be fixed by 888API. Never disable the SSRF validator to bypass such errors. The customer retains the previous refund and the original video-generation ID is reused.

## Stop repeated processing for deterministically inaccessible video outputs

The completed MiniMax H3 task returned HTTP literal-IP URLs on a custom port through both the direct result and authenticated content redirect. Previously all such addresses were rejected, including public media servers.

Completed-video retrieval now allows literal **public IPv4** addresses with HTTP or HTTPS and custom ports. This exception is limited to `videoContent`; image/general downloads retain their previous policy. Loopback, private, link-local, shared-address, documentation, benchmarking, multicast, reserved and Azure metadata addresses remain blocked, including URL-parser-normalized numeric loopback variants. IPv6 remains blocked. Literal IP validation avoids DNS rebinding for this new path. Every redirect is validated, downloads remain bounded to 64 MiB and five redirects, and the result must have an MP4 signature. Provider Bearer credentials are sent only to the original HTTPS 888API video endpoint, never to media IPs.

**Transport tradeoff:** HTTP media bytes and signed URL query parameters are unencrypted in transit to the provider media server. The app still serves the saved video to customers over its own HTTPS endpoint; the provider API key is never sent over HTTP. MP4 signature checking is a format check, not cryptographic integrity verification. An HTTPS provider output remains preferable.

Blocked private/reserved addresses still fail and refund when both routes are deterministically rejected. Public-server network failures retain transient retry behavior. No paid generation POST is repeated. Existing refunded jobs are not automatically recovered or charged again.

Deploy this change to the worker (and web service for Admin recovery). The live support API is read-only; tests mock network responses and do not prove the provider's actual server is public or reachable. Verify a subsequent authorized generation or Admin recovery after deployment. A local CMM refund does not reverse the provider's charge.

## Admin-controlled customer access

888API is off by default globally and per customer. On first deployment of the opt-in migration, both web and worker atomically disable the global 888API switch and reset existing customer 888API grants to off. A persisted migration marker prevents subsequent restarts from overwriting Admin choices. Other providers and already-submitted jobs are unchanged.

To allow use, enable the global 888API source in Admin, then enable 888API for the desired customer under Customers → Sources. New users have no 888API access until explicitly granted. Customer catalog, pricing and creation routes use that grant, and the worker requires it before submitting queued 888API jobs. Saving or syncing a token/catalog does not grant customer access.
